# 103차: 과거 성능 관측 재검증

런타임 변경 없이 보존된 원본 DLL과 현재 261bd35 산출물을 비교했다.
10만 회·warmup 10·표본 15·교차 3쌍·CPU mask 0x4·tiering off.
`compare_runs.py`의 원시 표본과 DLL 해시, 새 `summarize_runs.py`의
프로세스 중앙값 범위/할당 요약을 함께 보존했다.

| workload | 과거 ms | 현재 ms | 관찰 |
|---|---:|---:|---|
| int 하위 타입 비교 (90차) | 142.3510 | 145.6539 | +2.32%, 프로세스 중앙값 범위 겹침 |
| int 하위 타입/float (90차) | 145.0036 | 148.9636 | +2.73%, 이번 범위 분리 |
| 기본 숫자 대조군 (90차) | 145.5849 | 147.1603 | +1.08%, 범위 겹침 |
| OSError (85차) | 102.9722 | 101.7439 | -1.19% |
| OSError (86차) | 104.2833 | 101.7439 | -2.43% |
| ValueError 대조군 (85차) | 69.9041 | 67.6301 | -3.25% |

85→86차 OSError는 이번 +1.27%로 관측됐다. 99차의 비고정 -0.39%,
고정 +0.85%와 함께 보면 과거 +2.72%의 단일 원인 확정 근거는 부족하다.
현재 OSError가 빨라도 대조군이 같이 빨라서 이 수치를 특정 수정의 효과로
돌리지 않는다. 과거 binary는 이후의 호환성 수정을 포함하지 않는다.

비교 공통 진입점의 exact-number 조건, PyIntSubclass virtual slot,
TryCompareSpecial의 사용자 비교 cache와 native payload 위임을 재검토했다.
90차로 단순 복원하면 사용자 비교/NotImplemented 처리 자체가 달라지므로
성능만 보고 복원하지 않았다. 이번에는 근거 없는 추가 fast path를 넣지 않았다.

int 하위 타입 두 workload는 10만 회 전체에서 40 B 증가, 기본 숫자와
예외 두 workload는 할당 동일. 반복당 40 B 증가로 해석하지 않는다.
native probe는 클래스 1000개 1,032,000 B, 첫 비교 40,000 B,
반복 비교 0 B, invalid operator 8개와 C# override 12개 통과.
런타임 변경이 없어 직전 기본 회귀 175개·Godot 검증을 재사용했다.

결론: **int/float 잔여 비용과 역사적 지연 원인은 미해결**이다.
다음 실험은 현재 동작을 보존한 채 native slot/dispatch와 VM 전체 비용을
분리하는 것이다. 이번 재측정만으로 원인 또는 최적화 완료를 주장하지 않는다.
