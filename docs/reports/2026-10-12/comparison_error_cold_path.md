# 93차: 비교 오류 처리의 정상 경로 비용 제거

92차를 `1b8ff7c`로 로컬 커밋했다. 93차는 `3560d62`로 커밋하고 `origin/work/oserror-compatibility`에 푸시했다.

## 발견과 변경

92차에서 조회를 인라인한 결과, 잘못된 CompareOp를 검사하는 오류 분기도 PyIntSubclass.RichCompare 안에 들어왔다. 오류 메시지 보간의 임시 구조체 때문에 정상 비교에서도 스택 공간을 예약하고 초기화했다. Python의 정상 6종 비교에는 필요 없는 준비 작업이다.

운영 코드 변경은 PyObject.TryCompareSpecial의 오류 메시지 생성·throw를 NoInlining helper로 옮긴 것이다. 입력 검사는 그대로 유지하며, 유효하지 않은 값만 helper로 보낸다. CPython을 기준으로 검증한 비교 순서·반환값·바인딩·캐시 무효화에는 변화가 없다. 새 상태나 라이브러리 의존성도 없다.

## 기계어와 할당

.NET 8.0.31 Windows x64, TieredCompilation=0의 JIT 출력을 수정 전후로 대조했다.

- PyIntSubclass.RichCompare 자체의 기계어: 445→257 B. 새 helper와 다른 호출 함수를 합한 전체 코드 크기 비교는 아니다.
- 함수 진입 시 스택 예약: 80→32 B. 이 수치는 레지스터 push 등을 합한 전체 스택 사용량이 아니다.
- 정상 진입의 임시 공간 초기화 명령이 제거됐다.
- native 정수 payload의 RichCompare 위임이 call 후 반환에서 tail.jmp로 바뀌었다.

스택 비용과 GC 할당을 구분한다. 새 클래스 1,000개를 사용하는 기존 native probe는 양쪽 모두 클래스 생성 1,032,000 B, 최초 비교 40,000 B, 반복 비교 0 B다. 이번 단계에서 힙 할당이 줄었다고 주장하지 않는다.

## 회귀와 빌드

ComparisonCacheProbe에 C# 호출자용 잘못된 enum 값 검사를 추가했다. int 하위 타입과 일반 사용자 객체 각각에서 LT의 조회 실패 비트를 먼저 채운 뒤 -1, 6, 32, 64를 전달한다. 비트 shift가 순환하는 값도 오류 검사를 우회하지 않아야 한다. 수정 전후 모두 8개가 같은 ValueError와 메시지를 발생시켰다. 이는 Python 언어에 추가한 동작이 아니라 기존 native API 보존 검사다.

전체 회귀는 161개(완전 출력 일치 156개, 지정 변동 필드 제외 일치 3개, native 실패 보고 없음 2개)다. Godot는 SharpPy 소스를 직접 포함해 빌드하고 기본 17개 및 CPython 대조 17개, 총 34개를 실행한다. CPython 기준 버전은 3.12.15다.

최초 일반 빌드는 PEG 생성기 apphost 실행에서 Windows 애플리케이션 제어 오류 4551로 중단됐다. 사용자가 설정을 변경했다고 알린 뒤 같은 일반 빌드를 재시도했고 성공했다. 코드 생성 생략이나 보안 정책 변경을 수행하지 않았다. 최종 main·Godot 빌드는 경고·오류 0개이며, PerformanceHarness에는 기존 ByteArraySliceMutationProbe 관련 nullable 경고 2개가 남는다.

## 성능

Release, TieredCompilation=0, n=100,000, 워밍업 10회, 표본 15회, 독립 프로세스 3회씩 교대 실행한다. 빌드와 기능 검사를 마친 뒤 측정하며, 같은 하네스와 workload에서 SharpPy DLL만 바꾼다. 프로세스별 중앙값의 중앙값으로 비교한다. 기본 int 하위 타입 두 workload에는 90차 DLL도 포함해 누적 차이를 관찰한다. 모든 실행은 checksum을 검사한다.

| workload | 92차 ms | 수정 후 ms | 시간 변화 |
| --- | ---: | ---: | ---: |
| int_subclass_compare | 144.344 | 145.090 | +0.52% |
| int_subclass_float_compare | 146.657 | 143.985 | -1.82% |
| mixed_compare_small | 145.549 | 144.516 | -0.71% |
| integer_compare | 138.300 | 137.308 | -0.72% |
| user_compare | 82.296 | 84.176 | +2.28% |
| dictionary | 95.357 | 94.415 | -0.99% |

여섯 workload 모두 전후 프로세스 중앙값 범위가 겹친다. 사용자 비교의 +2.28%는 가능한 퇴행을 확인하기 위해 코드를 바꾸지 않고 시작 순서를 뒤집어 3쌍을 추가 측정했다. 재측정은 82.818→83.030 ms(+0.26%)이며 범위도 겹친다. 최초 측정을 대체하지 않고 둘 다 보존한다. 작은 증가·감소의 원인을 확정하지 않으며 이번 변경의 실행 시간 개선은 주장하지 않는다.

같은 측정의 90차 중앙값은 int 하위 타입 140.465 ms, int 하위 타입/float 141.768 ms다. 수정 후와의 차이는 +3.29%/+1.56%이고 범위는 겹친다. 92차 보고서의 +0.62%/+0.85%와 다른 표본이며, 잔여 비용이 정확히 고정된 비율이라고 해석하지 않는다. 성능 퇴행이 완전히 해소됐다는 주장도 하지 않는다.

숫자·사용자 비교 다섯 workload의 할당은 전후 동일하다. dictionary 할당 범위는 이전 30,854,592–30,867,192 B, 이후 30,854,592–30,864,912 B다. 이번에 확정한 이득은 오류 처리로 인해 정상 진입에 발생하던 준비 명령과 함수 내 코드·스택 예약 공간의 감소다.

원시 표본, DLL·소스 해시, 빌드 로그, JIT 출력과 실행 스크립트는 [검증 기록](round93-validation.json)에 보존한다.

## 남은 범위

다른 내장 비교 슬롯·명시적 type.__setattr__·정렬·수치 키 해시의 기존 불일치는 이번 수정 범위가 아니다. 이전 실패 재현을 유지하며 다음은 문자열의 반대편 비교 누락부터 확인한다. 비교의 잔여 비용은 계속 관찰하되 작은 실행 시간 차이를 코드 크기 감소와 구분해서 판단한다.
