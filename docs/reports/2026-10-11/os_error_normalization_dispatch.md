# 82차: OSError 생성 비용 분리와 불필요한 정규화 호출 제거

81차를 `52e3f7c`으로 커밋했다. 이번 런타임 변경은 정수 errno의 선택 방식을 유지하면서 winerror 정규화 함수를 인자 4~5개에서만 호출하는 두 곳의 조건 변경이다. 전체 VM 속도 개선이나 81차 시간 증가의 원인 해결을 주장하지 않는다.

## 조사와 최종 변경

81차 이전/이후 DLL을 같은 직접 생성·타입 호출·builtin 조회 후 호출 probe로 비교했다. errno 999의 직접 생성은 1.9564 → 2.1604 ms로 약 10.4% 증가했으며 추가 errno 비교의 비용과 일치하는 방향이다. 한 인자 OSError는 직접 생성 +4.2%, 타입 호출 -0.6%, 조회 후 호출 +2.4%로, 이전 VM 일반 생성 증가를 builtin 조회만의 문제로 확정할 수 없었다. 이 측정은 각 10만 회, 세 프로세스 중앙값의 중앙값이다.

정수 범위를 확인하고 int switch로 고르는 후보는 errno 999에서 약 7.8% 감소했지만 errno 1/2에서 약 17.3%/17.8% 증가해 제외했다. 인자 개수에 따라 생성자 전체를 조기 반환하도록 재배치한 후보도 일부 mapped errno를 느리게 해 제외했다. 최종 변경에는 이 후보들의 코드가 없다.

확인된 불필요 작업은 0~3개 또는 6개 이상 인자에서도 `NormalizeWindowsArguments`를 호출하는 것이었다. 이 함수는 해당 개수에서는 입력을 그대로 반환한다. OSError 팩터리와 직접 하위 타입 생성자에서 4~5개일 때만 호출하도록 바꿨다. 직접 생성자에서는 그 외 개수의 중복 Args 대입도 생략된다. base 생성자가 이미 같은 인자를 보존한다.

이 불필요 호출은 80차에도 있었으므로 81차의 증가를 발생시킨 원인이라고 말할 수 없다. 현재 구조에서 제거할 수 있는 작업을 줄인 별도 개선이다. bigint 비교 순서, bool 처리, kwargs 오류 우선순위, 오류 코드 매핑, 원본 인자 보존은 유지한다. 새 캐시·인스턴스 필드·라이브러리 의존성은 없다.

## 직접 생성 측정

하네스에 FileNotFoundError 대조군과 디렉터리 errno 20/21을 추가했다. 실행 옵션은 `--exception-factory-probe --directory-errno`다. ValueError는 대조군으로 유지한다. 각 배치에서 결과 타입과 인자 개수를 검사한다.

.NET 8.0.31 Release, TieredCompilation=0. 인자 배열을 측정 밖에서 만든 뒤 10만 회, 워밍업 5회, 표본 10회, 전후 3쌍을 교대 실행했다. 값은 프로세스별 중앙값 3개의 중앙값(ms)이다.

| 직접 생성 | 이전 | 최종 변경 | 변화 |
|---|---:|---:|---:|
| OSError, 한 문자열 | 1.2582 | 1.1309 | -10.1% |
| FileNotFoundError, 한 문자열 | 1.1942 | 1.0217 | -14.4% |
| OSError, errno 999 | 2.2325 | 2.0696 | -7.3% |
| OSError, errno 1 | 1.8143 | 1.6618 | -8.4% |
| OSError, errno 2 | 1.6486 | 1.5032 | -8.8% |
| OSError, errno 13 | 1.8792 | 1.6782 | -10.7% |
| OSError, errno 17 | 1.9030 | 1.7993 | -5.4% |
| OSError, errno 20 | 2.0059 | 1.9595 | -2.3% |
| OSError, errno 21 | 2.1349 | 2.0242 | -5.2% |

직접 생성 할당량은 전후 동일하다. ValueError 한 인자 대조군도 약 2.7% 감소했으므로 작은 차이는 측정 변동과 구분해야 한다. 이 수치를 VM 전체의 개선율로 사용하지 않는다.

## VM 대조

기존 fallback·한 문자열 생성 외에 `os_error_winerror` workload를 추가해 정규화가 실제로 필요한 인자 4개 경로도 확인했다. 의미적 결과는 회귀 파일이 검사하고 하네스는 반복 반환 합계를 검사한다.

동일 환경에서 반복 10만 회, 워밍업 10회, 표본 15회, 전후 3쌍 교대 실행했다. 빌드/기능 테스트와 성능 실행은 겹치지 않았다.

| workload | 이전 ms | 이후 ms | 변화 | 양쪽 할당량 |
|---|---:|---:|---:|---:|
| os_error_fallback | 72.7296 | 72.0405 | -0.95% | 25,904,120 B |
| os_error_construction | 97.7489 | 98.6652 | +0.94% | 41,104,040 B |
| os_error_winerror | 85.9956 | 86.7129 | +0.83% | 41,104,120 B |

프로세스 중앙값 범위는 모두 겹친다. 일반 생성의 쌍별 변화 방향도 섞였다. native 직접 생성은 전체 VM 반복 시간 중 작은 부분이므로 직접 생성 개선율만으로 전체 실행 시간 개선을 예상해서는 안 된다. 전체 VM의 유의한 개선은 확인하지 못했고, 앞서 관찰한 약 2.4% 증가의 원인도 확정하지 못했다.

## 검증과 남은 작업

- Release 빌드 성공.
- 실제 CPython 3.12.15와 전체 평가 148개: 출력 일치 143개, 변동 필드 제외 일치 3개, native 검사 실패 보고 없음 2개.
- 기존 OSError 회귀 4개가 인자 개수 경계, kwargs, bigint/bool/비정수, errno 하위 타입, Windows 변환을 포함한다. 새 의미 동작을 추가하지 않아 별도 중복 회귀 파일은 만들지 않았다.
- Godot 소스 포함 자체 빌드와 기본 17개 및 관련 4개, 총 21개 fixture 통과. 관련 4개의 CPython 출력 일치. 별도 SharpPy DLL 의존성 없음.
- `git diff --check` 통과. 비Windows 및 모바일 실기는 실행하지 않았다.

[검증 출력·최종 native 표본·VM 표본·진단 요약](round82-validation.json)을 보존한다. 제외한 후보의 상세 표본은 `.artifacts/round82-switch-*.json`, `.artifacts/round82-final-native-*.json`에 있으며 최종 후보 표본은 `round82-gated-native-*.json`이다.

후속 호환성 과제는 기존 `tests/compatibility/blocking_io_arguments.py`에 보존한 BlockingIOError의 characters_written 규칙과 남은 errno 하위 타입이다. VM 시간은 같은 조건으로 계속 관찰하되 미확정 원인을 단정해 구조를 크게 바꾸지 않는다.
