# 79차: OSError 생성 경로 성능 분리 측정

78차는 `2bc60a0`으로 커밋했다. 이번 변경은 일반 정수 errno에서 불필요한 bool 검사를 줄이는 것으로 한정한다. 78차에서 관찰한 약 5%의 VM 시간 증가는 이번 재측정에서 재현되지 않았다. 원인을 확정하거나 전체 VM 성능 회귀를 해결했다고 결론 내리지 않는다.

## 구현과 비교 기준

`PyOSError.FromArguments`에서 `PyInt`를 먼저 검사하고 별도 CLR 표현인 `PyBool`을 뒤에서 처리한다. errno 비교, 임의 정밀도 정수, True/False 처리, 인자 및 예외 결과는 유지한다. 캐시나 인스턴스 필드를 추가하지 않았다. 범위 검사와 정수 변환을 추가하는 후보는 일부 mapped errno 경로를 느리게 해 채택하지 않았다.

CPython 3.12.15 실행 결과와 고정 소스 `e848e4b09ca4bc67c0041c9ce7526dae471d4c36`의 `Objects/exceptions.c`를 기준으로 기존 OSError 회귀 파일을 대조했다. 이는 이미 지원하는 errno 선택 경로의 최적화이며 OSError 전체 호환성 완성을 뜻하지 않는다.

## 진단 방법

`ExceptionFactoryProbe`는 인자 배열을 측정 밖에서 준비하고 직접 생성, 타입 호출, builtin 조회 후 호출을 분리한다. 각 배치에서 최종 타입과 인자 개수를 검사한다. `--exception-factory-probe --mapped-errno`로 실행한다. 10만 회, 워밍업 5회, 표본 10회이며 전후 각각 3개 프로세스로 측정했다.

하네스의 `--remove-os-subtype-names` / `--add-os-subtype-names`는 해당 프로세스의 builtin 사전 크기 영향을 조사하기 위한 옵션이다. 추가 옵션은 두 이름에 OSError를 임시 대입하므로 정상 호환성 실행에 사용하면 안 된다. 이 진단의 workload는 두 이름을 호출하지 않는다. 제품 런타임의 등록 동작은 변경하지 않았다. 사전 이름을 추가/제거한 단일 대조에서는 시간이 일관되게 역전되지 않아 사전 크기를 원인으로 확정하지 못했다.

측정은 .NET 8.0.31 Release, TieredCompilation=0에서 수행했다. 성능 측정과 빌드/회귀 실행을 겹치지 않았고 실행 순서를 교대했다. 아래 값은 프로세스별 중앙값 3개의 중앙값이다.

## 직접 생성 측정

단위 ms, 각 10만 회. 인자 생성과 Python VM 실행을 제외한 측정이다.

| errno | 78차 | 이번 변경 | 시간 감소 |
|---|---:|---:|---:|
| 999 | 2.1269 | 1.9692 | 7.4% |
| 1 | 1.8809 | 1.8453 | 1.9% |
| 2 | 1.7711 | 1.5877 | 10.4% |
| 13 | 1.9653 | 1.7974 | 8.5% |
| 17 | 2.0549 | 1.9122 | 6.9% |

할당량은 동일하다. 호출/조회 경로의 결과도 원시 기록에 보존했다. 위 수치를 VM 전체의 속도 향상으로 해석하지 않는다.

## VM 전체 재측정

동일 하네스에 77차(`0688409`), 78차(`2bc60a0`), 이번 런타임을 각각 넣어 비교했다. 워밍업 10회, 10만 회 조건은 표본 15회, 1만 회 조건은 표본 10회다. 각 조건에서 세 버전의 순서를 회전시켜 3회 실행했다. 단위 ms.

| 반복 | workload | 77차 | 78차 | 이번 변경 |
|---|---|---:|---:|---:|
| 100,000 | os_error_fallback | 75.6125 | 75.0937 | 76.1910 |
| 100,000 | os_error_construction | 103.9659 | 102.0530 | 101.1523 |
| 10,000 | os_error_fallback | 7.54985 | 7.33770 | 7.46645 |
| 10,000 | os_error_construction | 10.18780 | 9.87755 | 10.02975 |

10만 회에서 이번 변경과 78차의 차이는 fallback +1.46%, construction -0.88%이며 프로세스별 범위가 겹친다. 78차에서 보고한 약 5% 증가는 당시와 같은 1만 회 조건에서도 재현되지 않았다. 측정 변동의 원인은 미확정이고, 전체 VM의 유의한 속도 개선을 주장하지 않는다.

모든 버전의 할당량은 동일하다. 10만 회 fallback 25,904,120 B, construction 41,104,040 B이며, 1만 회는 각각 2,481,272 B와 4,001,192 B다.

## 검증

- 전체 평가 146개: 출력 일치 141개, 변동 필드 제외 일치 3개, native 검사 실패 보고 없음 2개.
- Godot에 코드를 포함해 자체 컴파일/빌드 후 기본 17개와 추가 58개, 총 75개 fixture 통과. 별도 SharpPy DLL을 사용하지 않았다.
- Godot traceback fixture 1개는 CPython 파일 경로를 Godot `res://` 경로로 대응시킨 뒤 비교했다.
- CFG native probe PASS. `git diff --check` 통과.
- 기존 OSError 회귀 파일로 bool, 정수, 큰 정수, 다른 타입, kwargs, 타입 선택 및 인자 보존을 검증했다.

Windows에서 검증했다. 모바일 실기와 다른 OS 실행은 수행하지 않았다. 전체 표본과 비교 결과는 [원시 기록](round79-validation.json)에 보존한다.
